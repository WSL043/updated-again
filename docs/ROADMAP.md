# Updated Again 演进路线

这个项目的目标不是“假装有更新”，而是把更新本身做成一种可参与、可验证、可回放的娱乐媒介。

## 当前选择：声明式模块化单体

社区可以提交文案、视觉、按钮性格、桌面宠物等声明式配方；受信任的 GitHub Actions 将它们转换为签名更新胶囊。应用只解释已有能力，不执行投稿者提供的脚本。

我们暂不选择另外两条路线：

- **任意代码自动合并**：最自由，但投稿可以读取令牌、篡改发布流程或污染历史，破坏范围不再只是娱乐项目本身。
- **拆成多个服务和 Agent**：可扩展，但当前流量和玩法不值得承担部署、密钥、队列与监控成本。

保持一个仓库、一个签名账本和一组可插拔能力，是现在最容易理解、回滚和继续玩的结构。

## v0.2：社区自动驾驶

- Issue 表单直接生成签名胶囊，无需维护者逐条批准。
- 声明式 PR 完整 CI 通过后自动 squash 合并并删除分支。
- 自动提交破坏主分支时精确回滚，并留下可追踪 Issue。
- 每日健康巡检验证当日更新、公开站点指针和签名账本。

## v0.3：让历史也能玩

- 时间旅行：按日期、理由、作者和更新类型重放胶囊。
- 反更新：发布一个只撤销某次效果、但不删除历史的新胶囊。
- 更新季和连续剧：多个胶囊共享故事线、结局和社区投票。
- 本地导入导出：用户拥有自己的更新宇宙，同时保持官方账本只追加。

## v0.4：Agent 策展人

Agent 不直接修改可执行代码，只负责组合现有能力、生成候选文案、检测重复和调整配方权重。每次决定必须写入胶囊来源与随机种子，以便复现。

启用条件：社区候选量稳定超过人工可读范围，并且无需新增高权限密钥。

## v0.5：更高上限的能力协议

- 为新玩法定义版本化 JSON Schema 和迁移器。
- 在 Web Worker 或 WASM 沙箱中运行受限的确定性效果。
- 能力包必须声明权限、资源上限和降级显示。
- 旧客户端遇到未知玩法时仍能展示理由、作者和安全的文本版本。

## 衡量项目是否还“活着”

- 上海时区每天至少一个有效签名胶囊。
- 自动流程从投稿到公开可见的中位时间。
- 过去 30 天使用过的不同玩法类型，而不只是提交次数。
- 自动回滚次数、重复内容率以及无人处理的失败天数。

更新数量不是唯一目标；真正的上限来自“每次更新都能被理解、验证、重放，并且偶尔真的让人笑一下”。
